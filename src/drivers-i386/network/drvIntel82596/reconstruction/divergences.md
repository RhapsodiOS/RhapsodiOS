# drvIntel82596 reconstruction findings

## Baseline defects

The source-only baseline is not a valid package: it has no `.drvproj`/`.lksproj` hierarchy or shared headers, and its generated top-level Makefile source lists refer to nonexistent/retired files. The implementation imports nonexistent `driverkit/IOEthernetDriver.h` and declares `Intel82596 : IOEthernetDriver`, while reference metadata and the shipped driver use `Intel82596 : IOEthernet`. Several inline class declarations duplicate adapter declarations.

The baseline contains a stub initializer and local stubs/wrappers for network-buffer allocation, interrupt disabling, debugger locking, timeout registration/cancellation, run-state access and interrupt enable. Several names are real DriverKit superclass/category selectors (`allocateNetbuf`, `setRunning:`, `isRunning`, `reserveDebuggerLock`, `releaseDebuggerLock`), but they are not driver-owned implementations and must dispatch to the framework. `disableAllInterrupts` is absent from the reference selector set; the adapter interrupt methods own that behavior. The baseline also assigns unsupported bodies/return assumptions to `setThrottleTimers`, uses an incorrect `_nb_map` prototype and mismatched checksum/adapter types. None of those baseline bodies counts as function evidence.

The two source-map exceptions are the kernel-server/version methods emitted by the project framework. Binrecon marks every newly imported analyzer entry with `analyzer_agreement.generated=true`; this does not identify compiler-generated methods.

## Evidence and environment

* Reference identity is verified by the profile and the IDA export: 69,108 bytes, SHA-256 `BE6AED4264AB64119188AEE6A82AAB415940010DCF5705B6C241266AF45D0A11`.
* IDA 9.4 is installed and produced all 86 functions, including the address-zero Cogent probe. The approved plan template said 9.2; that path exists only as a license file on this machine. The profile therefore records the installed 9.4 `idat.exe`.
* Full pseudocode, disassembly, call edges and stored signatures are in ignored `tools/binrecon/out/intel82596/evidence/ida-functions.json`; no function failed decompilation.
* `analyze` successfully published IDA analysis and consensus reference files. It reported normalized-functions `FAIL` because there was no rebuilt artifact or comparison. This is the expected reference-only state, not a failed IDA analysis.
* The completed source map resolves 84 handwritten functions. The only two unmapped entries are the 12-byte `kernelServerInstance` and `driverKitVersionForIntel82596NetworkDriver` accessors generated by the Kernel Server project type; IDA confirms they return the driver instance address and version 500. The ledger records those as generated exceptions and the other 84 functions as control-flow-confirmed.
* The restored driver bundle's five tables, five localized strings, and Help document/resource files (31 files total) hash-match the reference package. `Intel82596Inspector.nib` is deliberately omitted with the separate inspector application; no inspector reference remains in the driver bundle.

## Native rebuild status

The host-side DriverTools archive is intact (20,243 bytes, SHA-256 `A40F11409DA054E568C362C3DEB2427D7CC894667CAAE68033822F14658487AA`). I restored that package in the VM copy and confirmed `gzip -t` succeeds and its archive contains all 60 entries. The reconstructed driver source and package script were staged at `/Disk/build/intel82596` in the copy.

The copied build volume itself is damaged. A read-only `fsck -n /dev/hd1a` reported widespread duplicate blocks and truncated inodes. I saved the writable overlay, ran `fsck -y` on the copy, and the checker marked the volume clean after salvaging 75,867 files. `rbuild` then began expanding dependencies but stopped before compilation: the guest reported `rbuild` and reads against `/Disk` in an uninterruptible I/O state, and no `.reloc` or driver package appeared in the output directory. The repaired overlay and the pre-repair backup are both preserved under `vm/work/rage-image-copy/`.

No rebuilt artifact is available for Binrecon comparison. Reference-only analysis still reports normalized-functions `FAIL` because its rebuilt input is unset; binary parity is unverified. The Rage source image was not changed.
