# SCSIServer PowerPC measurement

Reference: `Drivers/ppc/SCSIServer.config/SCSIServer_reloc`, SHA-256
`E813777748A4FAC9348AA1CF4E979863B96D75B09FDAC16DF586031499A122A2`.
`__TEXT,__text` spans `0x0`-`0x35b0` (13,744 bytes) and carries **69 defined
symbols**.

Analysis: IDA Professional 9.2 only. Ghidra and angr are i386-only in this tree
and their adapters reject a `ppc` profile.

**Nothing was compiled.** There is no PowerPC toolchain and no host C compiler in
this environment; `make` was not run. Every statement below rests on the
reference disassembly and on plain reading of our source.

## Commands and results

### Step 1 - reference analysis

```
BINRECON_REFERENCE=".../SCSIServer_reloc" PYTHONPATH=tools/binrecon \
  $VENVPY -m binrecon analyze --profile tools/binrecon/profiles/scsiserver-ppc.json
analysis complete; analyzers=1 comparisons=0 normalized-functions=FAIL
exit 1
```

Exit 1 and `normalized-functions=FAIL` are expected and not a defect: the
acceptance requirement compares a rebuilt binary against the reference, and there
is no rebuilt binary. The reference analysis itself completed and published.

The profile's `output_dir` is `../out/scsiserver-ppc`, relative to
`tools/binrecon/profiles/`, so the analysis lands in
**`tools/binrecon/out/scsiserver-ppc/`** - not `tools/out/scsiserver-ppc/` as the
task brief wrote it. The analysis JSON is
`tools/binrecon/out/scsiserver-ppc/published/analysis-reference-ida.json`.

### Step 2 - function count before mapping

```
functions: 206
unnamed  : 138
lowest   : 0x10
```

`lowest` is `0x10`, greater than 0: IDA has no function entry at `__text+0`,
exactly as the address-0 rule predicts.

All 138 unnamed functions are **exactly 16 bytes** - the PowerPC jump islands
(`lis r12 / ori r12 / mtctr r12 / bctr`) the linker emits after each calling
function.

### Step 3 - filter unnamed functions

```
$VENVPY tools/binrecon/filter_named_functions.py \
  tools/binrecon/out/scsiserver-ppc/published/analysis-reference-ida.json \
  tools/binrecon/out/scsiserver-ppc/analysis-named.json
exit 0

functions: 68
unnamed  : 0
lowest   : 0x10
input.sha256 unchanged: True
```

This is the first use of `filter_named_functions.py` on PowerPC and it worked
without modification. 206 - 138 = 68 named functions; 68 plus `deviceStyle` at 0
equals the 69 defined `__text` symbols.

### Step 4 - source map, primary route

The **primary route succeeded**; no fallback was needed and `--scope-to-objc`
was not used.

```
PYTHONPATH=tools/binrecon $VENVPY -m binrecon source-map \
  --reference-analysis tools/binrecon/out/scsiserver-ppc/analysis-named.json \
  --binary ".../SCSIServer_reloc" \
  --source-dir src/drvSCSIServer/SCSIServer.drvproj/SCSIServer.lksproj \
  --repo-root . \
  --objc-methods \
  --output src/drvSCSIServer/reconstruction/SCSIServer/source-map.json
exit 0
```

Because `--scope-to-objc` was omitted, the map's universe is all 68 named
functions, so the 35 C functions are measured alongside the 13 Objective-C
methods rather than being invisible.

One violation, and it is the known `deviceStyle` exclusion. The relocation

## The `+[SCSIServer deviceStyle]` exclusion

`+[SCSIServer deviceStyle]` is the first `__text` symbol, at address `0x0`. The
bytes there, read directly out of the file at `__text` file offset 2492:

```
9421ffe0   stwu  r1,-32(r1)
38600001   li    r3,1
38210020   addi  r1,r1,32
4e800020   blr
```

That is a complete 16-byte function returning 1. Our source has it at
`SCSIServer.m:37`:

```objc
+ (int)deviceStyle
{
    return 1;
}
```

The invariant check's message means only that **IDA's function list lacks an
entry at 0** - it is not evidence of an absent body. This is a known exclusion,
not a gap and not a phantom. It sits outside the map's universe because that
universe is built from IDA's function list, so it appears in neither `mapped`
nor `unmapped`, and the 68 in the tables above is 69 minus this one symbol.

## Confirmed gap list - six functions, not nine

The plan's table lists nine. The measurement finds **six**, and one of the six is
not on the plan's list. Both discrepancies are recorded here rather than
reconciled by assumption.

| Address | IDA size | Span | Name | Declared |
| --- | --- | --- | --- | --- |
| `0x0a70` | 276 | 356 | `_serverThreadFunc` | nowhere |
| `0x19bc` | 48 | 64 | `_IOTaskPortAllocate` | `IOTask.h:32` |
| `0x1c98` | 160 | 256 | `_IOConvertTaskPortToVMTask` | `IOTask.h:76` |
| `0x1d98` | 32 | 48 | `_IODestroyMappedVMTask` | `IOTask.h:85` |
| `0x1dc8` | 644 | 788 | `__io_task_notification` | `IOTask.h:94` |
| `0x20dc` | 480 | 576 | `_IORequestNotifyForClientTask` | `IOTask.h:105` |

"IDA size" is the analyzer's function size; "Span" is the distance to the next
named function, which includes the trailing 16-byte jump islands. The plan's
table quotes spans; the source map records IDA sizes. Both are right about
different things, and the **addresses agree exactly** for the five entries the
two lists share.

`_IORequestNotifyForClientTask` at `0x20dc` is the sixth gap. It is declared
`extern` in `IOTask.h:105` and nothing in the tree defines it; the header's own
comment says "NOT YET WRITTEN: declared extern only; nothing defines it yet." Its
address is exactly `0x1dc8 + 788`, the byte after the span attributed to
`__io_task_notification`, which is how it came to be folded into that entry and
dropped from the plan's list.

### The four Objective-C methods on the plan's list are already written

All four are in `mapped`, with a source site:

| Address | Name | Source |
| --- | --- | --- |
| `0x00e4` | `-[SCSIServer initFromDeviceDescription:]` | `SCSIServer.m:138` |
| `0x0654` | `-[IOSCSISession init]` | `IOSCSISession.m:57` |
| `0x068c` | `-[IOSCSISession initForDevice:result:]` | `IOSCSISession.m:79` |
| `0x06c4` | `-[IOSCSISession free]` | `IOSCSISession.m:105` |

Each has a real body, not a stub. The design document says these were "verified
absent by direct symbol lookup against all three `.m` files" using
`grep -c` on the symbol name; that method cannot work for an Objective-C method,
because the mangled form `-[IOSCSISession init]` never appears literally in a
`.m` file. The mapping is the evidence.

Whether those four bodies are *correct* is not settled here - this task measures
presence, not fidelity. They are candidates for review, not for writing from
scratch.

## Other facts that differ from the plan's premises

- **This driver has been measured with binrecon before.** An earlier pass left
  `src/drvSCSIServer/reconstruction/{source-map.json,ledger.json,divergences.md}`
  from plan `docs/superpowers/plans/2026-07-26-scsiserver-ppc-reconstruction.md`.
  That map has the same 41/27 split and the same address set as this one; only
  the `IOSCSISession.m` line numbers differ, by 4, from later edits. The new
  artifacts live under `reconstruction/SCSIServer/` per this plan; the flat ones
  are left untouched.
- **`IOTask.m` is already in `CLASSES`** - `PB.project` lists
  `SCSIServer.m, IOSCSISession.m, IOTask.m`. Seven of its functions map to the
  binary.
